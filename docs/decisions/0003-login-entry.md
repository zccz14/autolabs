# 0003 新设备的登录入口：走 Auth Mini 的远程批准，不自建登录

- 状态：已采纳（2026-11-08）
- 决策者：CZ

## 背景

AutoLabs 的身份只由 Auth Mini 签发。通行密钥（passkey）绑定在具体设备的认证器上，
所以一台没注册过通行密钥的设备——新笔记本、隔离的浏览器、CI 里的无头浏览器——会被登录页
直接挡住：既不能注册（需要已有会话），也不能验证（没有私钥）。

在一台没有通行密钥的设备上做界面核验时，这条硬墙把整条路堵死了。

## 决定

**不在 AutoLabs 里做任何形式的登录旁路，也不自建第二套登录。** 新设备走 Auth Mini 已有的
远程登录（remote login）：

1. 新设备打开登录页，选「在另一台设备上批准」，得到一个确认码；
2. 已经登录的设备打开 `https://auth.ntnl.io/remote-logins`，输入确认码、核对后批准；
3. 新设备用换码（exchange code）换到标准的令牌对，之后与通行密钥登录完全一样。

AutoLabs 要做的只有一件事：**在登录墙上把这条路指出来**。原来那句「Auth Mini 需要把
autolabs.ntnl.io 加进 audience 列表」只对配置错误有意义，对新设备毫无帮助，已换成远程登录的说明
与登录页链接。

## 为什么不自己解决

- 自建登录（甚至只是一个「开发用」的免登录开关）会让 AutoLabs 拥有一套与 Auth Mini 不一致的身份，
  门禁、令牌、审计的授权主体就不再是同一个。
- 远程登录的四步（start / claim / approve / exchange）是 Auth Mini 的公共接口，AutoLabs 复用它
  不需要新增任何服务端能力。
- 通行密钥仍然是默认路径：远程批准只是「这台设备暂时没有认证器」时的入口，不是降级。

## 后果

- 隔离浏览器可以在人工批准后登录，界面核验不必再打免登录补丁。
- 登录墙的文案从「配置提示」变成「下一步怎么做」，被挡住的人知道该去哪里。
- Auth Mini 若改动远程登录的路径或确认码格式，AutoLabs 只需更新这条文案，不涉及代码。
