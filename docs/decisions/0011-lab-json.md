# ADR 0011：lab.json —— 包自己说明怎么被评估

日期：2026-11-12

> 补 ADR 0010 第 1 条。那一条把评估入口放在项目设置里，等于「我替所有 lab 说一次它们怎么算」。这一条把这句话还给包本身。

## 背景

ADR 0010 落地之后，一条评估命令能跑起来了。但它挂在项目上，于是有两件事不成立：

- **历史复算不了。** `runs.metric_set_json` 钉得住口径版本，钉不住算法。今天重跑 lab-0012，用的是今天项目设置里那条命令，算出来的不是当年那个数字。
- **写实验的人不知道这个契约。** run thread 不知道自己的产物会被怎么评估，容易造出评估器拉不到的东西。

## 决定

1. **快照根目录的 `lab.json` 是这个包的门面。** 最小的一份：

   ```json
   { "evaluate": "python -m pack.evaluate" }
   ```

   想自己定超时：

   ```json
   { "evaluate": { "command": "python -m pack.evaluate", "timeout_seconds": 1800 } }
   ```

   超时被夹在 60 秒到 1 小时之间——上限是 eXe 的调用寿命，不是我们的偏好。

2. **算法跟着快照走。** 派发时的优先级：快照里的 `lab.json` > 项目设置 `eval_command`。快照不可变，所以历史指标第一次真的可复算：同一份代码 + 同一个入口 + 同一个数据 digest。

3. **坏掉的 `lab.json` 不悄悄退回。** 解析失败就直接把这一轮记成 `rejected`，evidence 写清是哪一处不对。悄悄退回项目命令会让「用的是哪套算法」变成一件靠猜的事——比拒绝更糟。

4. **派发脚本替命令干杂活。** 平台在设备上先建临时目录、把快照拉下来解开、`cd` 进去，然后才跑命令。所以工作目录是有定义的（`AUTOLABS_WORKDIR`，也就是包根），命令不用自己 mktemp、不用猜 cwd。这也是「实验包」这个说法能成立的原因：包被展开成一个目录，命令在里面跑。

5. **实际跑的命令落库。** `runs.eval_command` + `runs.eval_command_source`（`snapshot` / `project`）。一行字，换来「这个数字是哪条命令算的」不再是一段回忆。

6. **派单简报把 `lab.json` 列为硬要求。** 写不出这个文件的执行体，等于没把实验交代清楚。

## 为什么叫 lab.json，不叫 autolabs.json

`autolabs.json` 更无歧义，但 `lab.json` 更接近这个产品自己的话：一个实验包就是一个 lab。风险是**术语撞车**——地图上的一行也叫 lab（`lab-0004`）。文档里必须分开说：

- **lab-0004**：研究地图上的一行，一次已经结算的实验；
- **lab.json**：一个实验包的清单，说明这个包怎么被评估。

这两件事在同一个域里，但粒度不同：行是记录，包是代码。

## 代价

- **快照里能放可执行代码，现在会被执行。** 权限面没有变化——项目所有者本来就能改项目设置里的命令、也能改快照——但这条要写明白，别让人以为「快照只是文件」。
- **一个包一个入口。** 训练阶段和评估阶段分开的话，只能在命令里自己编排。
- **依赖不在契约里。** venv、`npm install`、数据版本，都得命令自己负责。`lab.json` 只说「跑什么」，不说「装什么」。
- **仍然是 1 小时。** 更长的回测得让命令自己后台跑再回报。
- **只有 Unix。** eXe 在 Windows 上走 `cmd /C`，这段脚本在那边跑不了。目前没人要求。

## 还没做

- `$schema` 与校验 URL：现在只是「平台自己认这个形状」，还没发布成对外规范。
- 多入口（`train` / `evaluate` / `smoke`）。
- 依赖声明（`runtime`、`requires`）。
- 把 `metric_set_json` 与 `eval_command` 一起做成「这一轮的算法指纹」，用于跨轮次的可比性判断。
